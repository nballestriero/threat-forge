# MR-0002ADR-0004REQ-0004 — Contratto condiviso di authoring documentale per MR, ADR e REQ

## Intent

Provide one IDE-independent local core for guided creation and modification of governed Macro-requirements, Decisions and Requirements.

## Functional obligation

- The governed document authoring core must support Macro-requirements, ADRs, Functional Requirements and Governance Requirements.
- The core must read applicable fields, controlled values, descriptions and relations from the canonical catalog.
- The core must read selectable governed identifiers from canonical registries.
- The core must derive identifiers, repository paths and derivable relations.
- The core must preview the complete structured record and Markdown body before writing.
- The core must separate preview from creation or modification.
- The core must require explicit confirmation before every repository mutation.
- The core must update all affected governed artifacts atomically.
- The core must execute applicable governed checks immediately after mutation.
- The core must report produced artifacts, executed checks and errors.
- CLI, editor adapters, the future web application and automations must share this core instead of reimplementing domain rules.

## Scope

- Includes: MR, ADR, Functional Requirement and Governance Requirement authoring
- Includes: temporary request documents as non-canonical inputs
- Includes: deterministic preview, confirmed writes and post-write checks
- Includes: shared consumption by CLI, IDE, web and automation adapters
- Excludes: request files as persistent canonical sources
- Excludes: surface-specific domain validation or enum ownership
- Excludes: unconfirmed or partial repository mutation

## Acceptance

- The requirement is accepted when each supported document type exposes only applicable and selectable values.
- The requirement is accepted when labels and descriptions match the shared canonical catalog.
- The requirement is accepted when preview leaves the repository unchanged.
- The requirement is accepted when an unconfirmed write is rejected.
- The requirement is accepted when a failed write leaves every affected artifact unchanged or absent.
- The requirement is accepted when applicable post-write checks execute and report their result.
- The requirement is accepted when identical requests produce identical plans for the same snapshot.
- The requirement is accepted when no consumer surface reimplements rules already owned by the core.
