# MR-0002ADR-0004REQ-0003 — Contratto di authoring guidato dei requisiti governati

## Intent

Provide one IDE-independent authoring core that prevents invalid identifiers, relations, controlled values and divergent Requirement representations.

## Functional obligation

- ThreatForge must provide a local governed Requirement authoring core independent from VS Code.
- The authoring core must read Macro-requirements, Decisions, parent Requirements and controlled values from their canonical sources.
- The authoring core must distinguish abstract Requirement categories from concrete persistable Requirement types.
- The authoring core must build a deterministic catalog of selectable identifiers, controlled values, descriptions and relation rules.
- The authoring core must derive active concrete Requirement models from the canonical document model index and requirement registry profile.
- Model-specific authoring behavior must be supplied by explicit providers checked against the canonical model inventory.
- The authoring core must build a deterministic JSON Schema projection from canonical sources.
- The authoring core must preview the complete YAML record and Markdown body before writing.
- The authoring core must require explicit confirmation before creation.
- The authoring core must create the registry record and Markdown body atomically.
- The authoring core must execute applicable governed checks immediately after creation.
- The authoring core must remain reusable by CLI and other local adapters.

## Scope

- Includes: authoring of every active concrete Requirement model with complete canonical provider coverage
- Includes: Macro-requirement, Decision and applicable parent selection
- Includes: deterministic identifier and body-path generation
- Includes: side-effect-free preview and confirmed creation
- Includes: post-creation governed verification
- Excludes: a custom VS Code extension
- Excludes: automatic Macro-requirement or Decision mutation
- Excludes: commit and push automation

## Acceptance

- The requirement is accepted when the same canonical snapshot produces the same catalog and JSON Schema.
- The requirement is accepted when only existing and applicable Macro-requirements, Decisions and parent Requirements are selectable.
- The requirement is accepted when only active concrete Requirement models with complete canonical provider coverage are persistable.
- The requirement is accepted when `specialized` is rejected as a concrete type or alias for `governance`.
- The requirement is accepted when preview displays complete artifacts without repository mutation.
- The requirement is accepted when creation requires explicit confirmation and remains atomic on failure.
- The requirement is accepted when applicable governed checks run and report their result after successful creation.
