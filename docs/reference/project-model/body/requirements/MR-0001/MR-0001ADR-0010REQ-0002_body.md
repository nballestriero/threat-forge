# MR-0001ADR-0010REQ-0002 — Registry-derived governed document model consumer coverage

## Intent

Ensure that every deterministic consumer derives the active governed document
model inventory from the canonical document model index while keeping only its
model-specific implementation providers explicit.

## Functional obligation

- ThreatForge must treat the canonical document model index as the only authoritative inventory of active governed document models for every deterministic consumer.
- A consumer must not define a separate list or fixed cardinality that claims which governed document models are canonical.
- A consumer with model-specific providers must keep an explicit provider catalog whose keys are checked against the canonical model inventory.
- Consumer provider coverage must require exactly one provider for every active canonical model.
- Consumer provider coverage must reject providers for model identifiers absent from the canonical index.
- Consumer projections of model identifiers must be compared with the canonical index rather than with a locally authored expected list.
- Requirement registry document-model dispatch must derive requirement type discriminators and model identifiers from the canonical requirement registry profile.
- Markdown assistance model validation, governed authoring contract validation and Target Project model validation must fail closed when canonical model coverage is incomplete.
- Extension of the canonical index must expose missing consumer support without requiring a consumer-local canonical inventory change.
- The canonical document model index must remain unchanged until a later governed model activation.

## Scope

- Includes: canonical model inventory derivation by deterministic consumers
- Includes: model-specific provider catalogs checked against the canonical inventory
- Includes: governed Markdown assistance coverage
- Includes: governed document authoring catalog and schema coverage
- Includes: Target Project complete-model validator coverage
- Includes: requirement registry discriminator-to-model dispatch
- Excludes: Security Requirement model registration
- Excludes: Security Requirement-specific validators or authoring behavior
- Excludes: migration or creation of Security Requirement records
- Excludes: archived legacy tooling

## Acceptance

- The requirement is accepted when no active consumer uses a fixed model count as canonical truth.
- The requirement is accepted when consumer model projections are compared with model identifiers derived from the canonical index.
- The requirement is accepted when every explicit model-provider catalog is checked for missing and unregistered model identifiers.
- The requirement is accepted when requirement registry dispatch derives supported discriminator values from canonical record variants.
- The requirement is accepted when a coherent synthetic additional model is accepted by the source loader but causes incomplete consumers to fail closed until their providers are supplied.
- The requirement is accepted when the current repository continues to pass without changing the canonical index.
