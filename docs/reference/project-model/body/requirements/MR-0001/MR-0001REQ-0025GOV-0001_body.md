# MR-0001REQ-0025GOV-0001 — Requirement controlled value validation

## Intent

The Requirement governance registry is only useful if future checks consume it and reject uncontrolled values.

Specialized requirements must not be able to introduce arbitrary suffixes such as `ABC`, and Requirement lifecycle statuses must not drift into ad-hoc values such as `done`, `validated`, or misspelled variants.

## Parent Functional Requirement

Parent functional requirement: `MR-0001REQ-0025`.

This specialized governance requirement hardens the Requirement governance registry by requiring deterministic validation of controlled values declared in that registry.

## Specialized Requirement

The project model must provide a deterministic validation path that checks Requirement registry controlled values against the Requirement governance registry.

The validator must reject unknown Requirement lifecycle statuses, unknown Requirement types when the `type` field is present, and unknown specialized Requirement suffix families.

## Scope

This requirement applies to future Requirement registry field validation.

It covers controlled Requirement status values, controlled Requirement type values, and specialized Requirement family suffixes. It also covers the rule that specialized requirements must reference a functional parent requirement.

It does not require the current micropasso to implement the validator, migrate legacy records without `type`, validate ADR statuses, or add new graph predicates for parent-child relations.

## Rules

- Future Requirement registry validation must load `docs/reference/project-model/registers/requirements/requirement-governance.registry.yml`.
- Requirement `status` values must exist in the controlled `requirement_statuses` list.
- Requirement `type` values, when present, must exist in the controlled `requirement_types` list.
- Requirement records without `type` are transitional legacy records until a dedicated append-first migration makes `type` explicit.
- Specialized Requirement identifiers must contain a suffix family registered in `specialized_requirement_families`.
- Specialized Requirement records must declare `parent_requirement_id`.
- Specialized Requirement parents must exist and must resolve to functional Requirement records.
- The validator must report deterministic diagnostics that include the offending Requirement id, field, and registry path.
- The validator must not duplicate controlled values outside the Requirement governance registry.

## Acceptance Criteria

```gherkin
Scenario: Unknown specialized Requirement suffix is rejected
  Given a Requirement registry declares a specialized requirement id with suffix ABC
  And ABC is not listed in the Requirement governance registry
  When the Requirement registry validator runs
  Then validation fails with a deterministic diagnostic for the unknown suffix family

Scenario: Unknown Requirement lifecycle status is rejected
  Given a Requirement registry declares status done
  And done is not listed in the Requirement governance registry
  When the Requirement registry validator runs
  Then validation fails with a deterministic diagnostic for the unknown status value
```

## Verification Expectation

A future deterministic gate must validate Requirement registry controlled values against the Requirement governance registry and include negative fixtures for unknown lifecycle status, unknown Requirement type, unknown specialized suffix family, and specialized parent mismatch.
