# MR-0001ADR-0009REQ-0001GOV-0001 — Deterministic Security Requirement model and cross-model coherence validation

## Intent

Make malformed or incoherent Security Requirement models, registry
records, Markdown bodies, parent relations and finding derivations
deterministically detectable through stable repository diagnostics.

## Governance obligation

- The governed document model source check must validate security-requirement as a distinct canonical logical model.
- The Security Requirement model validation must consume the canonical model registry shared requirement registry profile dedicated body profile and controlled value sets.
- Every Security Requirement diagnostic rule must have a stable canonical identifier.
- Security Requirement validation must enforce the identifier pattern formed by one Functional Requirement identifier followed by SEC and a four-digit sequence.
- Security Requirement validation must enforce requirement_type security and the canonical registry record field set.
- Cross-model validation must resolve exactly one Functional Requirement parent.
- Cross-model validation must enforce identical Macro-requirement and Decision ownership between a Security Requirement and its Functional Requirement parent.
- Cross-model validation must require at least one accepted finding reference.
- Finding references must be resolved and evaluated through the canonical identity lifecycle and acceptance semantics owned by the common analysis model.
- Security Requirement validation must not redefine Finding identity lifecycle acceptance or resolution semantics.
- Markdown validation must enforce the canonical Security Requirement heading sections order cardinalities content kinds and governed reference positions.
- Security Requirement negative fixtures must declare the stable rule identifiers they expect to trigger.

## Verification obligations

- The verification must confirm that one canonical Security Requirement logical model and its representation profiles are accepted.
- The verification must confirm that a valid Security Requirement registry record resolves its Functional Requirement parent.
- The verification must confirm that valid parent and child records share Macro-requirement and Decision ownership.
- The verification must confirm that accepted finding references are resolved through the common analysis model boundary.
- The verification must confirm that every Security Requirement diagnostic contains a known stable rule identifier.
- The verification must confirm that model-specific negative fixtures trigger their declared rule identifiers.
- The verification must cover registry identity parent ownership finding derivation body structure and controlled value failures.
- The verification must reject duplicate Security Requirement rule identifiers.

## Failure conditions

- The verification must fail when a Security Requirement model or representation profile is missing inconsistent or references an unknown canonical source.
- The verification must fail when a Security Requirement identifier does not extend its Functional Requirement parent identifier with SEC and a four-digit sequence.
- The verification must fail when a Security Requirement registry record does not use requirement_type security.
- The verification must fail when a Security Requirement parent is missing unresolved or is not a Functional Requirement.
- The verification must fail when a Security Requirement and its parent differ in Macro-requirement or Decision ownership.
- The verification must fail when a Security Requirement has no accepted finding reference.
- The verification must fail when a finding reference is unresolved or is not accepted according to the common analysis model.
- The verification must fail when Security Requirement validation attempts to redefine Finding lifecycle or acceptance semantics.
- The verification must fail when a Security Requirement body omits duplicates or reorders a canonical section.
- The verification must fail when a governed reference appears in a position not allowed by the Security Requirement body profile.
- The verification must fail when an emitted diagnostic omits a stable rule identifier.
- The verification must fail when a negative fixture does not trigger every rule identifier it declares.
