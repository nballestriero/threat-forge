# MR-0001ADR-0009REQ-0001GOV-0001 — Deterministic Security Requirement model and cross-model coherence validation

## Intent

Make malformed or incoherent Security Requirement models, registry records, Markdown bodies, functional parent relations and accepted Finding derivations deterministically detectable through stable repository diagnostics while preserving ownership boundaries between governed requirements, Common Findings and methodology plugins.

## Governance obligation

- The governed document model source check must validate security-requirement as a distinct canonical logical model.
- Security Requirement model validation must consume the canonical model registry shared requirement registry profile dedicated body profile controlled value sets and governed entity reference boundary.
- Every Security Requirement diagnostic rule must have a stable canonical identifier.
- Security Requirement validation must enforce the identifier pattern formed by one Functional Requirement identifier followed by SEC and a four-digit sequence.
- Security Requirement validation must enforce requirement_type security and the canonical registry record field set.
- The canonical Security Requirement registry record field set must contain id title status requirement_type macro_requirement_id decision_id parent_requirement_id and body_path.
- The canonical Security Requirement registry record field set must not contain a Finding-reference field.
- Cross-model validation must resolve exactly one Functional Requirement parent.
- Cross-model validation must enforce identical Macro-requirement and Decision ownership between a Security Requirement and its Functional Requirement parent.
- Markdown validation must enforce the canonical Security Requirement heading sections order cardinalities content kinds and governed reference positions.
- The Parent Functional Requirement section must contain exactly one governed Functional Requirement reference matching parent_requirement_id.
- The Finding derivation section must contain at least one governed Common Finding reference.
- Duplicate Common Finding references within one Security Requirement must be rejected.
- Finding references must be resolved and evaluated through the canonical identity source discovery review-state and eligibility semantics owned by the common analysis model.
- Every referenced Common Finding must have current review_state accepted.
- Every referenced Common Finding must contain an affected_subjects entry whose kind is functional_requirement and whose id equals the Security Requirement parent_requirement_id.
- Common Finding references must be accepted only in the governed Finding derivation reference position of the Security Requirement body profile.
- Security Requirement validation must preserve the navigable relation from each referenced Common Finding to its originating Analysis Record.
- Security Requirement validation must not require method identifiers method payloads classifications applicability rules failure modes attack classes or plugin diagnostics in the Security Requirement source.
- Security Requirement validation must not execute methodology plugins require plugin availability or reinterpret method-specific payload semantics.
- Security Requirement validation must not redefine Common Finding identity review-state values eligibility source discovery or resolution semantics.
- Any reverse Common Finding to Security Requirement index must be derived from validated Finding sources and valid Security Requirement body references.
- Any reverse Common Finding to Security Requirement index must not be treated as an authored canonical registry.
- Security Requirement negative fixtures must declare the stable rule identifiers they expect to trigger.

## Verification obligations

- The verification must confirm that one canonical Security Requirement logical model and its representation profiles are accepted.
- The verification must confirm that a valid Security Requirement registry record uses the canonical field set without Finding identifiers and resolves its Functional Requirement parent.
- The verification must confirm that valid parent and child records share Macro-requirement and Decision ownership.
- The verification must confirm that the body parent reference matches parent_requirement_id.
- The verification must confirm that one or more unique accepted Common Finding references are resolved through the common analysis model boundary.
- The verification must confirm that every accepted Finding used by the Security Requirement identifies the Functional Requirement parent as an affected governed subject.
- The verification must confirm that every selected Common Finding remains traceable to its originating Analysis Record.
- The verification must confirm that Security Requirement validation remains independent from methodology plugin execution and availability.
- The verification must confirm that a reverse Finding-to-Security-Requirement projection is derived from canonical sources without introducing an authored Common Finding registry.
- The verification must confirm that every Security Requirement diagnostic contains a known stable rule identifier.
- The verification must confirm that model-specific negative fixtures trigger their declared rule identifiers.
- The verification must cover registry identity field set parent ownership Finding derivation body structure reference position and controlled value failures.
- The verification must reject duplicate Security Requirement rule identifiers.

## Failure conditions

- The verification must fail when a Security Requirement model or representation profile is missing inconsistent or references an unknown canonical source.
- The verification must fail when a Security Requirement identifier does not extend its Functional Requirement parent identifier with SEC and a four-digit sequence.
- The verification must fail when a Security Requirement registry record does not use requirement_type security.
- The verification must fail when a Security Requirement registry record omits a canonical field contains an unknown field or contains a Finding-reference field.
- The verification must fail when a Security Requirement parent is missing unresolved or is not a Functional Requirement.
- The verification must fail when a Security Requirement and its parent differ in Macro-requirement or Decision ownership.
- The verification must fail when the Parent Functional Requirement body reference is missing duplicated unresolved or differs from parent_requirement_id.
- The verification must fail when the Finding derivation section contains no Common Finding reference.
- The verification must fail when a Common Finding reference is duplicated unresolved or not accepted according to the common analysis model.
- The verification must fail when a referenced Common Finding does not identify the Security Requirement parent Functional Requirement among its affected governed subjects.
- The verification must fail when a Common Finding reference appears outside the governed Finding derivation position.
- The verification must fail when a Security Requirement source contains method-specific fields or requires method-specific payload interpretation.
- The verification must fail when Security Requirement validation requires execution or availability of the originating methodology plugin.
- The verification must fail when Security Requirement validation attempts to redefine Common Finding identity review-state eligibility source discovery or resolution semantics.
- The verification must fail when a purported Common Finding inventory is authored as a second canonical source rather than derived from validated sources.
- The verification must fail when a Security Requirement body omits duplicates or reorders a canonical section.
- The verification must fail when an emitted diagnostic omits a stable rule identifier.
- The verification must fail when a negative fixture does not trigger every rule identifier it declares.
