# MR-0001REQ-0026GOV-0001 — Programmer Governed Development Guide

## Intent

Programmers need an operational guide that explains how to make governed changes without bypassing the project model.

The guide must make the routine path explicit: decision first when needed, small requirement, graph traceability, implementation only after the contract exists, source-code traceability, verification gates, and governed commit/push.

## Parent Functional Requirement

Parent functional requirement: `MR-0001REQ-0026`.

This specialized governance requirement applies the governed guide-placement rule to the programmer-facing development guide.

## Specialized Requirement

The project must provide a programmer governed development guide under the Diátaxis how-to space.

The guide path must be:

```text
docs/how-to/governed-development/programmer-governed-development-guide.md
```

The guide must explain how programmers should work with ADRs, requirements, graph relations, implementation artifacts, JSDoc traceability, validation gates, and the governed repository operation runner.

## Scope

This requirement applies to human programmer workflow guidance for threat-forge and future child projects governed by threat-forge.

It covers the operating sequence and architectural boundaries programmers must respect.

It does not implement validators, frontend components, backend services, child-project scaffolding, or threat-analysis logic.

## Rules

- The programmer guide must live under `docs/how-to/governed-development/`.
- The guide must instruct programmers to prefer `npm run repo:check` and `npm run repo:commit-push -- "<message>"` for routine governed repository operations.
- The guide must state that direct Git operations are exceptions for bootstrap, recovery, or emergency maintenance.
- The guide must require ADR and Requirement records before implementation when a change introduces or changes governed behavior.
- The guide must require graph relations before implementation work is treated as governed.
- The guide must require source artifacts to declare implemented requirements and derived decisions through JSDoc when applicable.
- The guide must preserve the backend architecture boundary: Node.js, Zod contracts, OpenAPI HTTP contract, factory/composition root, Controller → Service → Port → Adapter layering, and middleware only for cross-cutting concerns.
- The guide must preserve the frontend boundary: React components consume view models and API/client ports instead of reading YAML, Markdown, Git, graph files, or filesystem paths directly.
