# MR-0001ADR-0009REQ-0001 — Canonical Security Requirement logical model and governed representations

## Intent

Make Security Requirement identity, functional parentage, accepted Finding derivation, methodology-independent obligation and governed Markdown representation explicit and machine-readable before authoring or validating concrete security obligations.

## Functional obligation

- ThreatForge must define security-requirement as a canonical logical governed document model extension.
- The canonical document model registry must associate security-requirement with the shared requirement registry profile and a dedicated Security Requirement Markdown body profile.
- The requirement registry profile must define a security-requirement record variant discriminated by requirement_type security.
- A Security Requirement identifier must extend its parent Functional Requirement identifier with the segment SEC followed by a four-digit sequence.
- Every Security Requirement registry record must contain exactly id title status requirement_type macro_requirement_id decision_id parent_requirement_id and body_path according to the security-requirement record variant.
- Every Security Requirement registry record must contain exactly one parent_requirement_id referencing a governed Functional Requirement.
- Every Security Requirement must inherit the Macro-requirement and Decision ownership of its Functional Requirement parent.
- Finding references must not be duplicated in the Security Requirement registry record.
- The Security Requirement body profile must define canonical sections for Intent, Parent Functional Requirement, Finding derivation, Security obligation, Scope and Acceptance in deterministic order.
- The Parent Functional Requirement section must contain exactly one governed reference that mirrors the Functional Requirement identified by parent_requirement_id.
- The Finding derivation section must contain one or more governed Common Finding references.
- Every Common Finding referenced by a Security Requirement must resolve through the common analysis model.
- Every Common Finding referenced by a Security Requirement must have current review_state accepted.
- Every Common Finding referenced by a Security Requirement must include the Security Requirement parent Functional Requirement among its affected governed Functional Requirements.
- Every Common Finding selected by the author as part of the Security Requirement derivation must appear exactly once in the Finding derivation section.
- The Finding derivation section must permit explanatory prose that states how the selected accepted Findings justify the Security obligation without copying method-specific classifications or payloads.
- The Security Requirement body profile must represent its parent Functional Requirement and accepted Common Findings through governed references resolved by their owning canonical models.
- The Security Requirement model must preserve a navigable provenance chain from the Security Requirement through each Common Finding to its originating Analysis Record.
- The Security Requirement model must not require method identifiers method payloads classifications applicability rules failure modes attack classes or plugin diagnostics in either its registry record or Markdown body.
- Security Requirement validation must not execute a methodology plugin require plugin availability or reinterpret methodology-specific payload semantics.
- Repository-contained validated .analysis-finding.yml files must remain the canonical Common Finding sources.
- ThreatForge must permit derivation of a consultable reverse projection from validated Finding sources and governed Security Requirement body references without creating a second canonical inventory.
- The Security Requirement model must remain structurally distinct from Functional Requirement and Governance Requirement models.
- The Security Requirement model must not redefine Common Finding identity review-state values acceptance eligibility source discovery or reference resolution semantics.
- The controlled requirement_type value set must include security as the discriminator of the Security Requirement record variant.

## Scope

- Includes: Security Requirement logical model definition
- Includes: Security Requirement variant in the shared requirement registry profile
- Includes: Registry structure aligned with existing requirement variants
- Includes: Dedicated Security Requirement Markdown body profile
- Includes: SEC-based child identity derived from the Functional Requirement parent
- Includes: Exactly one Functional Requirement parent
- Includes: Parent reference mirrored between registry and body
- Includes: One or more accepted Common Finding references in the body
- Includes: Parent-to-Finding affected-subject coherence
- Includes: Navigable Finding and Analysis Record provenance
- Includes: Macro-requirement and Decision ownership coherence
- Includes: Controlled security requirement type value
- Includes: Derived consultable Finding-to-Security-Requirement projection
- Excludes: Common Finding identifiers stored in the Security Requirement registry record
- Excludes: Central Common Finding registry
- Excludes: Repository checker implementation
- Excludes: Negative verification fixtures
- Excludes: Governed authoring support for Security Requirement documents
- Excludes: Migration or creation of concrete Security Requirement records
- Excludes: Governance Requirement children of Security Requirements
- Excludes: Common Finding review workflow transition authorization or remediation lifecycle
- Excludes: Policy standard compliance baseline or contract-only Security Requirement derivation
- Excludes: Non-security Finding domains
- Excludes: STRIDE and STRIDE-AI classifications or rules
- Excludes: Automatic Finding discovery consolidation or Security Requirement generation

## Acceptance

- The requirement is accepted when the canonical document model registry contains an active security-requirement model entry with resolvable registry and Markdown body profiles.
- The requirement is accepted when the canonical representation profile registry contains a dedicated Security Requirement Markdown body profile.
- The requirement is accepted when the shared requirement registry profile contains a security-requirement record variant with the canonical structural fields and no Finding-reference field.
- The requirement is accepted when the Security Requirement identity pattern is derived from one Functional Requirement identifier followed by SEC and a four-digit sequence.
- The requirement is accepted when the Security Requirement registry record requires exactly one Functional Requirement parent and shares its Macro-requirement and Decision ownership.
- The requirement is accepted when the Security Requirement body profile declares the six required sections in deterministic order.
- The requirement is accepted when the Parent Functional Requirement section mirrors parent_requirement_id through exactly one governed reference.
- The requirement is accepted when the Finding derivation section requires one or more unique governed references to accepted Common Findings.
- The requirement is accepted when every referenced Common Finding includes the parent Functional Requirement among its affected governed Functional Requirements.
- The requirement is accepted when the provenance of each selected Finding remains navigable to exactly one originating Analysis Record without method-specific fields in the Security Requirement.
- The requirement is accepted when Security Requirement validation depends on the common Finding boundary rather than plugin execution or plugin availability.
- The requirement is accepted when reverse Finding-to-Security-Requirement traceability can be derived without a central Finding registry or mutation of Finding sources.
- The requirement is accepted when the controlled requirement_type value set contains security.
