# MR-0001ADR-0009REQ-0001 — Canonical Security Requirement logical model and governed representations

## Intent

Make Security Requirement structure, identity, parentage, finding
derivation and Markdown representation explicit and machine-readable
before authoring or validating concrete security obligations.

## Functional obligation

- ThreatForge must define security-requirement as a fifth canonical logical governed document model.
- The canonical document model registry must associate security-requirement with the shared requirement registry profile and a dedicated Security Requirement Markdown body profile.
- The requirement registry profile must define a security-requirement record variant discriminated by requirement_type security.
- A Security Requirement identifier must extend its parent Functional Requirement identifier with the segment SEC followed by a four-digit sequence.
- Every Security Requirement registry record must contain exactly one parent_requirement_id referencing a Functional Requirement.
- Every Security Requirement registry record must contain one or more accepted finding references whose canonical identity lifecycle and resolution are owned by the common analysis model.
- Every Security Requirement must inherit the Macro-requirement and Decision ownership of its Functional Requirement parent.
- The Security Requirement body profile must define canonical sections for Intent, Parent Functional Requirement, Finding derivation, Security obligation, Scope and Acceptance.
- The Security Requirement body profile must represent its parent Functional Requirement and accepted findings through governed references resolved by their owning canonical models.
- The Security Requirement model must remain structurally distinct from Functional Requirement and Governance Requirement models.
- The Security Requirement model must not redefine Finding identity lifecycle acceptance or resolution semantics.
- The controlled requirement_type value set must include security as the discriminator of the Security Requirement record variant.

## Scope

- Includes: Security Requirement logical model definition
- Includes: Security Requirement variant in the shared requirement registry profile
- Includes: Dedicated Security Requirement Markdown body profile
- Includes: SEC-based child identity derived from the Functional Requirement parent
- Includes: Functional parent and finding derivation fields
- Includes: Macro-requirement and Decision ownership coherence
- Includes: Controlled security requirement type value
- Excludes: Repository checker implementation
- Excludes: Negative verification fixtures
- Excludes: Governed authoring support for Security Requirement documents
- Excludes: Migration or creation of concrete Security Requirement records
- Excludes: Governance Requirement children of Security Requirements
- Excludes: Definition or implementation of canonical Finding identity lifecycle and resolution
- Excludes: STRIDE and STRIDE-AI classifications or rules

## Acceptance

- The requirement is accepted when the canonical document model registry contains five logical models including security-requirement.
- The requirement is accepted when the canonical representation profile registry contains a dedicated Security Requirement Markdown body profile.
- The requirement is accepted when the shared requirement registry profile contains a security-requirement record variant.
- The requirement is accepted when the Security Requirement identity pattern is derived from one Functional Requirement identifier followed by SEC and a four-digit sequence.
- The requirement is accepted when the Security Requirement record requires one Functional Requirement parent and at least one accepted finding reference owned by the common analysis model.
- The requirement is accepted when canonical coherence rules require the Security Requirement and its parent to share Macro-requirement and Decision ownership.
- The requirement is accepted when the Security Requirement body profile declares the six required sections in deterministic order.
- The requirement is accepted when the controlled requirement_type value set contains security.
