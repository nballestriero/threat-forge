# MR-0001ADR-0004REQ-0002 — Catalogo canonico dei campi controllati e dei metadati di presentazione

## Intent

Expose one surface-independent catalog for governed controlled fields, allowed values and the metadata needed to understand and select them.

## Functional obligation

- The Project Model must derive one canonical controlled-field catalog from governed taxonomy and document-model sources.
- Each controlled field entry must identify its canonical name, governing source, application context, requiredness and applicable field relations.
- Each controlled value entry must identify its machine value, readable label, description and selection or persistence eligibility.
- Each controlled value entry must identify abstract, forbidden, deprecated or historical states when applicable.
- Each controlled value entry must expose explicitly allowed or forbidden aliases when applicable.
- Each controlled value entry must expose optional presentation color as non-normative metadata.
- CLI, VS Code, API and web surfaces must consume the catalog or deterministic projections instead of defining independent enums or descriptions.
- Markdown body prose must not become a canonical source for structured controlled fields.

## Scope

- Includes: controlled fields for Macro-requirements, Decisions and Requirements
- Includes: governance registries, implementation trace and check results
- Includes: labels, descriptions, aliases and optional presentation metadata
- Includes: deterministic projections for editor, CLI, API and web consumers
- Excludes: surface-specific copies of domain enums
- Excludes: Markdown prose as the authority for structured field values

## Acceptance

- The requirement is accepted when every controlled field in scope has one unambiguous canonical source.
- The requirement is accepted when every selectable value has a readable label and description.
- The requirement is accepted when abstract or forbidden values are not selectable or persistable.
- The requirement is accepted when aliases are explicit rather than inferred by consumer code.
- The requirement is accepted when one catalog can drive editor schemas, CLI validation, API contracts and web presentation.
- The requirement is accepted when a canonical-source change deterministically changes or invalidates its projections.
- The requirement is accepted when missing or ambiguous provenance prevents catalog generation.
