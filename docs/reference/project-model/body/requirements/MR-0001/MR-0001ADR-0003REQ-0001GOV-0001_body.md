# MR-0001ADR-0003REQ-0001GOV-0001 — Coerenza deterministica tra registro, requisiti e codice

## Status

Draft.

## Requirement

Il registro di tracciabilita implementativa deve essere controllabile deterministicamente contro i registri requisiti e contro gli artefatti implementativi presenti nel repository.

Il controllo deve verificare almeno:

- ogni requisito collegato dal registro esiste in un registro requisiti;
- ogni record ha uno stato ammesso;
- ogni artefatto pianificato puo mancare dal repository senza bloccare il controllo;
- ogni artefatto pianificato non implementato produce un warning deterministico;
- ogni artefatto dichiarato implementato esiste al percorso dichiarato;
- ogni artefatto implementato dichiara nel codice i requisiti che implementa o supporta;
- il codice non dichiara requisiti inesistenti;
- il registro e il codice non divergono sui requisiti collegati.

Il controllo puo essere realizzato da un singolo tool o da piu tool coordinati da un orchestratore.

## Rationale

Il registro di tracciabilita implementativa e utile solo se rimane sincronizzato con i requisiti e con il codice.

Questo requisito specializzato trasforma il registro in una fonte controllabile: gli artefatti pianificati diventano warning visibili, mentre gli artefatti dichiarati implementati devono essere verificabili.

## Scope

In scope:

- validazione dei requisiti collegati;
- validazione dello stato dei record;
- validazione dei percorsi pianificati o implementati;
- warning per artefatti pianificati non completati;
- errore per artefatti dichiarati implementati ma mancanti;
- confronto tra registro e dichiarazioni di tracciabilita nel codice.

Out of scope:

- validare la qualita interna del codice implementato;
- decidere il formato definitivo dei report;
- rendere bloccanti i warning per artefatti pianificati;
- sostituire i controlli specializzati dei singoli tool.

## Acceptance Criteria

Il requisito e soddisfatto quando un controllo deterministico puo:

- fallire se il registro cita un requisito inesistente;
- emettere warning se un artefatto pianificato non e ancora presente;
- fallire se un artefatto dichiarato implementato non esiste;
- fallire se un artefatto implementato non dichiara i requisiti collegati;
- fallire se il codice dichiara requisiti inesistenti;
- produrre un report leggibile delle incoerenze rilevate.

## Executable Examples

```gherkin
Scenario: Planned artifact is not implemented yet
  Given the implementation trace registry contains a planned tool
  And the planned tool path does not exist in the repository
  When the implementation trace check runs
  Then the check reports a warning
  And the check does not fail only because of that planned artifact
```

```gherkin
Scenario: Implemented artifact path is missing
  Given the implementation trace registry contains an implemented tool
  And the implemented tool path does not exist in the repository
  When the implementation trace check runs
  Then the check fails
```

```gherkin
Scenario: Linked requirement does not exist
  Given the implementation trace registry links an artifact to a requirement id
  And no requirement registry contains that requirement id
  When the implementation trace check runs
  Then the check fails
```

## Notes

Gli esempi eseguibili sono inclusi perche preparano direttamente casi positivi e negativi per il futuro controllo deterministico.

Non ogni regola interna del controllo deve diventare un requisito separato. Questo requisito governa la proprieta complessiva di coerenza tra registro, requisiti e codice.
