# MR-0005ADR-0003REQ-0001 — Common methodology plugin contract and governed resolution

## Intent

Provide one common versioned boundary through which ThreatForge resolves a selected methodology, validates method-owned analysis data and determines the eligibility of accepted analysis records to produce common Finding candidates without importing concrete method semantics into the common core.

## Functional obligation

- ThreatForge must define one versioned common methodology plugin API contract owned by MR-0005.
- The common analysis core must own the governed plugin catalog, plugin resolution, compatibility evaluation, validation orchestration, common result envelope and Finding-derivation eligibility gate.
- Each governed plugin catalog entry must bind one unique method identifier to its owning Macro-requirement, plugin entry point, plugin API version, published payload schema and availability classification.
- ThreatForge must establish plugin availability only through the explicit governed plugin catalog.
- ThreatForge must not infer plugin availability through filesystem scanning, package naming conventions, network lookup or implicit imports.
- The initial compatibility evaluation must require exact equality between the cataloged plugin API version and the API version supported by the common core.
- Each methodology plugin must own its method payload schema, method-specific validation and derivation semantics, stable diagnostics, classifications, applicability rules, failure modes and attack classes.
- The common core must validate the Analysis Record envelope, canonical identity, lifecycle state and governed subject references.
- A methodology plugin must validate only the selected method payload and method-owned semantics.
- Common-core diagnostics and methodology-plugin diagnostics must use distinct stable namespaces.
- A methodology plugin must receive immutable canonical inputs.
- A methodology plugin must not modify Analysis Records, Base Analysis sources, governed requirements or common Findings.
- Validation orchestration must return one deterministically ordered result that exposes common-record validity, plugin resolution, compatibility, payload validity or unverified status, Finding-derivation eligibility and stable diagnostics.
- An unavailable or incompatible plugin must leave common-record validity independently inspectable, leave the method payload unverified and block deterministic Finding derivation.
- ThreatForge must permit deterministic Finding derivation only when the common Analysis Record is valid, every governed subject resolves, the explicit derivation state is accepted, the selected plugin is available and compatible, the method payload is valid and returned candidates satisfy the common Finding boundary.
- The same canonical input and plugin version must produce the same ordered candidates and diagnostics.
- A fixture-only plugin must remain non-production.
- A fixture-only plugin must not claim implementation or certification of a real methodology.

## Scope

- Includes: Common methodology plugin API ownership
- Includes: Governed plugin catalog and explicit resolution
- Includes: Exact initial plugin API compatibility
- Includes: Method payload schema publication
- Includes: Common validation-result envelope and layered diagnostics
- Includes: Finding-derivation eligibility gate
- Includes: Fixture-only plugin classification
- Excludes: Concrete STRIDE or STRIDE-AI classifications and rules
- Excludes: Plugin loader validator or fixture-plugin implementation
- Excludes: Process isolation remote installation hot loading or plugin marketplace behavior
- Excludes: Redefinition of the common Finding model
- Excludes: Automatic mutation of upstream governed sources

## Acceptance

- The requirement is accepted when one common versioned plugin API contract separates common-core ownership from methodology-specific ownership.
- The requirement is accepted when every resolvable methodology plugin is represented by one explicit catalog entry containing the canonical method owner entry point API version payload schema and availability classification.
- The requirement is accepted when plugin resolution ignores implicit filesystem package and network discovery mechanisms.
- The requirement is accepted when compatibility is accepted only when the cataloged plugin API version exactly equals the common-core API version.
- The requirement is accepted when validation produces one deterministic layered result that distinguishes common-record validity plugin resolution compatibility payload verification derivation eligibility and the distinct stable diagnostic namespaces.
- The requirement is accepted when an unavailable or incompatible plugin leaves the common record inspectable while marking its payload unverified and blocking Finding derivation.
- The requirement is accepted when Finding derivation is eligible only after all common record subject lifecycle plugin compatibility payload validity and common Finding boundary conditions succeed.
- The requirement is accepted when repeated processing of the same canonical input with the same plugin version produces the same ordered candidates and diagnostics without mutating governed sources.
- The requirement is accepted when a fixture-only plugin can be used only in controlled test or case-study contexts and cannot be selected or represented as a production implementation of a real methodology.
