# MR-0005ADR-0003REQ-0001GOV-0001 — Deterministic methodology plugin contract and governed resolution validation

## Intent

Make methodology plugin catalog resolution compatibility validation derivation eligibility and fail-safe behavior deterministically verifiable without importing concrete methodology semantics into the common core.

## Governance obligation

- Methodology plugin contract validation must consume the canonical common plugin API contract the governed plugin catalog the methodology-specific analysis record model and the common Finding boundary.
- Every methodology plugin contract diagnostic rule must have one stable canonical identifier.
- Common-core diagnostics and methodology-plugin diagnostics must remain in distinct stable namespaces.
- The governed plugin catalog must reject duplicate method identifiers duplicate plugin entry points and incomplete catalog entries.
- Every catalog entry must bind one method identifier to exactly one owning Macro-requirement one plugin entry point one plugin API version one published payload schema and one availability classification.
- Plugin resolution must use only the governed plugin catalog.
- Plugin resolution must not infer availability through filesystem scanning package naming conventions network lookup or implicit imports.
- Initial plugin compatibility validation must require exact equality between the cataloged plugin API version and the API version supported by the common core.
- Common validation orchestration must validate the Analysis Record envelope canonical identity lifecycle state and governed subject references independently from the selected method payload.
- A resolved compatible plugin must validate only its selected method payload and method-owned semantics.
- Plugin invocation must receive immutable canonical inputs.
- A methodology plugin must not modify Analysis Records Base Analysis sources governed requirements or common Findings.
- Validation orchestration must emit one deterministic layered result exposing common-record validity plugin resolution compatibility payload verification Finding-derivation eligibility and stable diagnostics.
- An unavailable or incompatible plugin must leave common-record validity independently inspectable mark the selected method payload as unverified and block Finding derivation.
- Finding derivation eligibility must remain false unless the common Analysis Record is valid every governed subject resolves the explicit derivation state is accepted the selected plugin is available and compatible the method payload is valid and every returned candidate satisfies the common Finding boundary.
- Repeated processing of the same canonical input with the same plugin version must produce the same ordered candidates and diagnostics.
- A fixture-only plugin must remain non-production.
- A fixture-only plugin must not claim implementation or certification of a real methodology.
- Negative fixtures must declare the stable rule identifiers they expect to trigger.
- Implementation traces must link the plugin catalog resolver compatibility validator orchestration boundary fixture plugin negative fixtures and verification suites to this Governance Requirement.

## Verification obligations

- The verification must accept one canonical common plugin API contract and one valid governed catalog entry.
- The verification must confirm that common-core and methodology-plugin diagnostic namespaces are distinct and stable.
- The verification must reject duplicate method identifiers duplicate plugin entry points incomplete catalog entries and ambiguous method ownership.
- The verification must confirm that resolution succeeds only for plugins declared in the governed catalog.
- The verification must confirm that filesystem package network and implicit-import discovery paths are not used.
- The verification must accept compatibility only when the cataloged plugin API version exactly equals the common-core API version.
- The verification must confirm that common-record validation remains independently inspectable when plugin resolution or compatibility fails.
- The verification must confirm that an unavailable or incompatible plugin leaves the method payload unverified and Finding derivation ineligible.
- The verification must confirm that a compatible plugin validates only its selected method payload and method-owned semantics.
- The verification must confirm that plugin invocation leaves every canonical input and governed source unchanged.
- The verification must confirm that the layered result exposes every required state and deterministically orders candidates and diagnostics.
- The verification must compare repeated processing of identical canonical inputs with the same plugin version for deterministic equivalence.
- The verification must exercise every Finding-derivation eligibility precondition independently and in combination.
- The verification must reject a returned candidate that violates the common Finding boundary.
- The verification must confirm that a fixture-only plugin cannot be resolved as a production implementation of a real methodology.
- The verification must confirm that every emitted diagnostic contains a known stable rule identifier in the correct namespace.
- The verification must confirm that negative fixtures trigger every declared rule identifier.
- The verification must reject duplicate plugin-contract diagnostic rule identifiers.

## Failure conditions

- The verification must fail when the canonical common plugin API contract or governed plugin catalog is missing or inconsistent.
- The verification must fail when a catalog entry is incomplete duplicated ambiguously owned or refers to an unresolved payload schema.
- The verification must fail when plugin availability is inferred outside the governed plugin catalog.
- The verification must fail when compatibility is accepted without exact plugin API version equality.
- The verification must fail when common-record validity cannot be inspected independently after plugin resolution or compatibility failure.
- The verification must fail when an unavailable or incompatible plugin verifies the method payload or permits Finding derivation.
- The verification must fail when a plugin validates or controls common Analysis Record fields governed subject resolution lifecycle state or common Finding semantics.
- The verification must fail when plugin invocation modifies a canonical input or governed source.
- The verification must fail when repeated processing of identical canonical inputs with the same plugin version produces different ordered candidates or diagnostics.
- The verification must fail when Finding derivation becomes eligible while any required common record subject lifecycle plugin compatibility payload validity or Finding-boundary condition is false.
- The verification must fail when a returned candidate violates the common Finding boundary.
- The verification must fail when a fixture-only plugin is selectable or represented as a production implementation of a real methodology.
- The verification must fail when an emitted diagnostic omits its stable identifier or uses the wrong diagnostic namespace.
- The verification must fail when duplicate plugin-contract diagnostic rule identifiers are published.
- The verification must fail when a negative fixture does not trigger every stable rule identifier it declares.
- The verification must fail when implementation traceability for the plugin catalog resolver compatibility validator orchestration boundary fixture plugin negative fixtures or verification suites is missing.
