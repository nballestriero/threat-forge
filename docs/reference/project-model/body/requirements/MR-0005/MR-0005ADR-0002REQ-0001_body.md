# MR-0005ADR-0002REQ-0001 — Canonical common analysis finding record and review state

## Intent

Make findings produced by different analysis methods comparable,
reviewable and traceable to their analytical origin, affected system
knowledge and governed functional behavior.

## Functional obligation

- ThreatForge must define a canonical common analysis finding record.
- Every common finding must have a stable canonical identifier.
- Every common finding must reference exactly one originating governed analysis record.
- Every common finding must reference one or more affected Base Analysis Elements relations or governed Functional Requirements.
- Every common finding must reference at least one affected governed Functional Requirement before entering the accepted state.
- Every common finding must describe one concrete threat scenario.
- Every common finding must describe the expected consequences of the threat scenario.
- Every common finding must preserve supporting rationale or evidence.
- Every common finding must use one controlled review state selected from proposed accepted and rejected.
- Finding review state must be explicitly recorded.
- Finding review state must not be inferred automatically from finding content governed references or method-specific data.
- Findings produced by different analyses must retain independent canonical identities.
- Shared subjects consequences or governed references must not automatically merge findings.
- Method-specific classifications applicability rules failure modes and attack classes must remain outside the common finding record.
- An accepted common finding must be referenceable by one or more governed Security Requirements.
- Creating or referencing a Security Requirement must not modify the originating finding.

## Scope

- Includes: Common analysis finding identity and record structure
- Includes: Originating governed analysis reference
- Includes: Affected Base Analysis and Functional Requirement references
- Includes: Threat scenario consequences rationale and evidence
- Includes: Proposed accepted and rejected review states
- Includes: Explicit recorded finding state
- Includes: Independent finding identity
- Includes: Security Requirement derivation boundary
- Excludes: Documentation gap record implementation
- Excludes: STRIDE classifications
- Excludes: STRIDE-AI classifications failure modes or attack classes
- Excludes: Quantitative risk scoring
- Excludes: Automatic finding acceptance
- Excludes: Automatic finding merge or deduplication
- Excludes: Security Requirement document model implementation
- Excludes: Complete multi-role approval workflows
- Excludes: Reviewer identity or evidence of human participation
- Excludes: Authorization and audit of finding state transitions

## Acceptance

- The requirement is accepted when a canonical common finding record has a stable identifier and one originating analysis reference.
- The requirement is accepted when a common finding records affected governed system knowledge and Functional Requirements.
- The requirement is accepted when an accepted finding retains at least one affected Functional Requirement.
- The requirement is accepted when a common finding records one threat scenario its consequences and supporting rationale or evidence.
- The requirement is accepted when the controlled finding review state contains proposed accepted and rejected.
- The requirement is accepted when the accepted state is explicitly recorded and is never inferred automatically.
- The requirement is accepted when findings from different analyses retain independent identities unless explicitly consolidated through a later governed process.
- The requirement is accepted when method-specific interpretations remain outside the common finding record.
- The requirement is accepted when an accepted finding can be referenced without mutation by one or more Security Requirements.
