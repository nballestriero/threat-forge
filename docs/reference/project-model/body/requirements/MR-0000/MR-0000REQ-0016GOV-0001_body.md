# MR-0000REQ-0016GOV-0001 — Append-first semantic diff and confirmation manifest guard

## Intent

The append-first guard must compare protected records semantically and require explicit, reviewable confirmation for destructive changes.

This specialized requirement narrows `MR-0000REQ-0016` so the future implementation can declare a precise JSDoc requirement instead of pointing only to the broader append-first guard requirement.

## Parent Functional Requirement

Parent functional requirement: `MR-0000REQ-0016` — Deterministic append-first guard for canonical registries and graph files.

## Specialized Requirement

The append-first protected record guard must perform semantic record-level comparison between a Git baseline and the current working tree, allow append-only additions by default, and require explicit confirmation records for modifications or deletions of protected records.

## Scope

This requirement applies to the future append-first guard implementation for canonical project-model registries and graph files.

The first implementation should cover the protected record classes declared by append-first governance: decision registries, requirement registries, graph node and SPO relation records, body-format profiles, graph node type registry records, and SPO predicate registry records.

This requirement does not implement the guard. It defines the focused behavior that the future guard tool must implement and verify.

## Rules

- The guard must parse protected YAML files and compare records by stable logical identity, not by raw text lines.
- The guard must classify new records as append additions.
- The guard must classify changed existing records as modifications.
- The guard must classify missing existing records as deletions.
- Append additions must be allowed by default.
- Modifications and deletions must fail unless they are covered by an explicit confirmation manifest.
- Confirmation manifests must identify the source path, record identity, change type, affected fields when applicable, reason, and human approval marker.
- Graph SPO relations must be identified by their logical triple identity: subject, predicate, and object.
- The guard must report diagnostics with enough detail for humans and LLM-assisted workflows to understand what changed and what confirmation is required.
- The guard must not treat formatting-only YAML changes as protected record modifications when the parsed semantic record is unchanged.

## Acceptance Criteria

```gherkin
Scenario: Append-only protected registry update passes
  Given a protected requirement registry baseline
  When the current registry only adds a new requirement record
  Then the append-first guard reports the added record
  And the guard passes without requiring a confirmation manifest

Scenario: Protected record modification requires confirmation
  Given a protected requirement registry baseline containing an existing requirement
  When the current registry changes a protected field of that requirement
  And no matching confirmation manifest exists
  Then the append-first guard fails
  And the diagnostic names the source path, record id, changed field, old value, and new value

Scenario: Confirmed protected record deletion passes
  Given a protected graph baseline containing an SPO relation
  When the current graph removes that relation
  And a matching confirmation manifest records the deletion reason and approval marker
  Then the append-first guard accepts the deletion
  And the diagnostic reports that the destructive change was explicitly confirmed
```

## Verification Expectation

A future implementation must include deterministic checks or fixtures for append-only additions, unconfirmed modifications, unconfirmed deletions, confirmed modifications, confirmed deletions, graph SPO relation identity matching, and formatting-only YAML changes that do not alter semantic records.
