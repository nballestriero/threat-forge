# MR-0000REQ-0015GOV-0001 — Append-first protected change confirmation manifest

## Intent

Intentional modifications or deletions of protected project-model records must remain possible, but they must be explicit, reviewable, and machine-checkable.

This specialized requirement narrows `MR-0000REQ-0015` so the future confirmation-manifest implementation can declare a precise JSDoc requirement instead of pointing only to the broader confirmation requirement.

## Parent Functional Requirement

Parent functional requirement: `MR-0000REQ-0015` — Explicit confirmation for protected record modifications and deletions.

## Specialized Requirement

The system must define a deterministic confirmation-manifest model for intentional protected record modifications and deletions detected by the append-first guard.

A confirmation manifest must identify the protected source, logical record identity, change type, affected fields when applicable, reason, and human approval marker needed to authorize a non-append change.

## Scope

This requirement applies to future append-first confirmation manifests used by MR-0000 governance checks.

It covers the structure and minimum semantics that the append-first guard must require before accepting a protected `modify` or `delete` change.

It does not yet implement manifest parsing, schema validation, or acceptance logic. Those belong to a later operational micropasso.

## Rules

- Confirmation manifests must be stored as governed project-model artifacts under a declared project-model path.
- Each confirmation manifest must have a stable confirmation identifier.
- Each confirmed change must identify the protected source path.
- Each confirmed change must identify the protected record using the same logical identity used by the append-first guard.
- Each confirmed change must declare the change type as `modify` or `delete`.
- A `modify` confirmation must list the affected protected fields when field-level comparison is available.
- A graph SPO relation confirmation must identify the relation by subject, predicate, and object.
- Each confirmation manifest must include a human-readable reason.
- Each confirmation manifest must include an explicit human approval marker.
- A generic force flag must not be sufficient to bypass append-first protection.
- Confirmation manifests must authorize only the specific protected changes they name.

## Acceptance Criteria

```gherkin
Scenario: Confirmed protected requirement title modification is accepted
  Given a protected requirement registry record is modified intentionally
  And a confirmation manifest names the source path, record id, change type, changed field, reason, and approval marker
  When the append-first guard evaluates the change
  Then the guard accepts that specific modification

Scenario: Unmatched confirmation manifest does not bypass protection
  Given a protected graph relation is deleted
  And a confirmation manifest names a different relation
  When the append-first guard evaluates the change
  Then the guard rejects the deletion

Scenario: Generic force bypass is not allowed
  Given a protected record is modified
  When the user provides only a generic force marker
  Then the append-first guard rejects the modification
  And the diagnostic requests a specific confirmation manifest entry
```

## Verification Expectation

A future implementation must include deterministic checks or fixtures for accepted confirmed modifications, accepted confirmed deletions, unmatched confirmations, incomplete confirmations, graph SPO relation confirmations, and rejection of generic force-style bypasses.
