# MR-0000REQ-0015GOV-0002 — Self-contained append-first confirmation manifest storage model

## Intent

Append-first confirmation manifests must remain simple operational records that authorize specific protected record modifications or deletions without creating a second registry/body maintenance burden.

This specialized requirement clarifies the storage model for confirmation manifests before the append-first guard is extended to read and match them.

## Parent Functional Requirement

Parent functional requirement: `MR-0000REQ-0015` — Explicit confirmation for protected record modifications and deletions.

## Specialized Requirement

The system must treat each append-first confirmation manifest as a self-contained governed YAML record discovered from a declared confirmation-manifest directory and validated against the canonical confirmation-manifest schema.

Confirmation manifests must not require a separate manifest registry or a separate Markdown body. The manifest YAML file is the complete governed record for the specific protected changes it confirms.

## Scope

This requirement applies to append-first confirmation manifests used to authorize protected `modify` or `delete` changes detected by MR-0000 append-first checks.

It covers only the storage and discovery model for confirmation manifests. It does not implement manifest parsing, schema validation, or protected-change matching logic.

## Rules

- Confirmation manifests must be stored as standalone YAML files under the declared project-model confirmation-manifest directory.
- The manifest YAML file is the complete governed operational record.
- Confirmation manifests must not require a separate registry entry.
- Confirmation manifests must not require a separate Markdown body.
- The append-first guard must discover confirmation manifests by scanning the declared directory, not by reading a manually maintained manifest registry.
- Each confirmation manifest must be schema-validated before it is allowed to authorize any protected change.
- A confirmation manifest may include a long-form explanatory field inside the YAML record when a longer reason is needed.
- The self-contained storage model must avoid duplicate canonical sources for the same confirmation.

## Acceptance Criteria

```gherkin
Scenario: Confirmation manifest is self-contained
  Given a protected requirement registry record is intentionally modified
  And a confirmation manifest YAML file names that protected change and includes the required reason and approval fields
  When the append-first guard evaluates confirmation manifests
  Then the guard treats that YAML file as the complete confirmation record

Scenario: Separate manifest registry is not required
  Given a valid confirmation manifest YAML file exists in the declared confirmation-manifest directory
  And no separate confirmation manifest registry entry exists
  When the append-first guard discovers confirmations
  Then the guard can still validate and consider the manifest

Scenario: Separate manifest body is not required
  Given a valid confirmation manifest YAML file includes all schema-required confirmation data
  And no Markdown body exists for that manifest
  When the append-first guard validates confirmations
  Then the guard does not require a separate body file
```

## Verification Expectation

A future implementation must include deterministic checks or fixtures proving that confirmation manifests are discovered from the declared directory, validated as self-contained YAML records, and not dependent on a separate registry or Markdown body.
