# MR-0000REQ-0007GOV-0001 — Thin MR-0000 project-model gate runner orchestration

## Intent

The broad MR-0000 runner requirement must be narrowed before a concrete runner tool is introduced.

This specialized requirement defines the first operational runner as a thin orchestrator over existing project-model gates, so future source code can cite a precise requirement instead of relying only on `MR-0000REQ-0007`.

## Parent Functional Requirement

Parent functional requirement: `MR-0000REQ-0007` — Runner unico MR-0000 per i gate di coerenza del project model.

## Specialized Requirement

The system must provide a single MR-0000 project-model gate runner that invokes the existing governed documentation and project-model validation commands in a deterministic order, reports which gate failed, and propagates failure through a non-zero process exit code.

The runner must remain a thin orchestration layer and must not duplicate the validation logic already owned by specialized validators.

## Scope

This requirement applies to the future first operational implementation of the MR-0000 project-model gate runner.

It covers orchestration behavior, failure reporting, command sequencing, and the boundary between the runner and existing validators.

It does not implement the runner, add a package script, change existing validator behavior, or introduce new validation semantics.

## Rules

- The runner must be located under `backend/tools/MR-0000/` when implemented.
- The runner must execute existing gates by invoking their command entrypoints or tool entrypoints instead of reimplementing their checks.
- The runner must use a deterministic gate order documented by the implementation micropasso.
- The runner must print a readable label before or with each gate result.
- If any gate fails, the runner must stop or report failure in a deterministic way and exit with a non-zero code.
- If all orchestrated gates pass, the runner must exit with code zero.
- The runner must remain suitable for local handoff verification and future CI use.
- The runner implementation must include JSDoc traceability to this requirement, `MR-0000/ADR-0003`, and `MR-0000`.
- Adding the runner source file must be done in a later micropasso after this requirement and its graph relations exist.

## Acceptance Criteria

```gherkin
Scenario: All orchestrated gates pass
  Given the repository contains the existing governed project-model validation gates
  When the MR-0000 gate runner is executed
  And every orchestrated gate passes
  Then the runner reports each gate result
  And the runner exits with code zero

Scenario: One orchestrated gate fails
  Given the repository contains the existing governed project-model validation gates
  When the MR-0000 gate runner is executed
  And one orchestrated gate fails
  Then the runner reports the failing gate label
  And the runner exits with a non-zero code

Scenario: Runner remains a thin orchestrator
  Given specialized validators own the actual validation rules
  When the MR-0000 gate runner is implemented
  Then it invokes the existing validators or command entrypoints
  And it does not duplicate their validation logic inline
```

## Verification Expectation

A future implementation must be verified by executing the MR-0000 gate runner successfully on the current repository and by ensuring the runner source declares JSDoc traceability to this specialized requirement.
