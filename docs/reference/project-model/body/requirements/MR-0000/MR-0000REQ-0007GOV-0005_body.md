# MR-0000REQ-0007GOV-0005 — Direct Git operation exception policy

## Intent

Routine repository changes must use the governed repository operation runner instead of direct `git commit` and `git push` commands.

This specialized governance requirement makes the operational rule explicit: direct Git commit or push is reserved for bootstrap, runner recovery, or documented emergency maintenance when the governed runner cannot be used safely.

## Parent Functional Requirement

Parent functional requirement: `MR-0000REQ-0007` — Runner unico MR-0000 per i gate di coerenza del project model.

## Specialized Requirement

The project model must define the governed repository operation runner as the canonical path for routine commit and push operations.

Direct `git commit` or `git push` usage must be treated as an exception path limited to bootstrap, recovery, or emergency cases where the governed runner is unavailable or would prevent repairing itself.

## Scope

This requirement applies to local development, handoff, and routine project-model repository operations.

It covers the operational policy for choosing `npm run repo:check` and `npm run repo:commit-push -- "<message>"` over direct Git commit or push commands.

It does not define remote branch protection, CI enforcement, server-side hooks, or a permanent technical block against all direct Git use by an operator with shell access.

## Rules

- Routine governed repository changes must be verified with `npm run repo:check` before commit/push when practical.
- Routine governed repository commit/push operations must use `npm run repo:commit-push -- "<message>"`.
- Direct `git commit` or `git push` is allowed only for bootstrap, recovery, or emergency maintenance.
- Any direct Git exception must be explainable in the handoff context or commit rationale.
- Handoff instructions must prefer the governed runner commands over raw Git commands.
- The policy must remain aligned with the repository operation governance guard and its negative fixture coverage.

## Acceptance Criteria

```gherkin
Scenario: Routine governed change uses the runner
  Given a routine governed project-model change is ready
  When the operator prepares to commit and push
  Then the documented canonical path is `npm run repo:commit-push -- "<message>"`
  And raw `git commit` or `git push` is not the routine path

Scenario: Runner recovery allows direct Git as an exception
  Given the governed repository operation runner is unavailable or broken
  When a focused repair is needed to restore the governed path
  Then direct Git may be used as an exception
  And the exception is described in the handoff context or commit rationale

Scenario: Handoff instructions prefer governed operations
  Given a handoff describes how to verify or commit repository changes
  When it lists routine repository operation commands
  Then it prefers `npm run repo:check` and `npm run repo:commit-push -- "<message>"`
```

## Verification Expectation

Running `npm run repo:check` must pass after this requirement is added, and the working plan must state that routine commits and pushes use the governed runner while direct Git remains an exception for bootstrap, recovery, or emergency maintenance.
