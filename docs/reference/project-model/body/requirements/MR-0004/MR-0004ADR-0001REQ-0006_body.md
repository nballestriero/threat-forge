# MR-0004ADR-0001REQ-0006 — Caso di studio didattico interno e riproducibile

## Intent

Include in the ThreatForge repository one versioned and portable Target Project case study that can be used to exercise, explain and evaluate the governed workflow without replacing the capability to generate and analyze independent external Target Projects.

## Functional obligation

- The ThreatForge repository must contain one versioned Target Project case study dedicated to the documentation-to-Base-Analysis demonstration.
- The internal case study must be stored outside canonical ThreatForge project-model sources, implementation tools and automated-test fixtures.
- The internal case study must be distinguishable from external Target Projects created in user-selected destinations.
- The initial internal case-study corpus must be created from the maintained Target Project generator capability rather than from an unrelated manually assembled structure.
- The maintained Target Project generator must continue to support explicit external destinations independently of the internal case study.
- The internal case study must not become the generator template source or the only supported Target Project corpus.
- The internal case study must be versioned directly by the ThreatForge repository.
- The internal case study must not contain a nested Git repository.
- The internal case study must be portable across repository locations and machines without repository-user-specific absolute paths.
- The internal case study must be validatable by the existing Target Project checker using its repository-contained path as the explicit target root.
- The internal case study must be usable as a governed VS Code Target Project workspace without duplicating engine-owned contracts, models, profiles, controlled values or analysis rules.
- The internal case-study documentation must permit deliberate refinement during the demonstration when documentary ambiguity prevents a defensible Base Analysis.
- Changes made for didactic clarity must remain governed Target Project changes.
- Changes made for didactic clarity must pass the same canonical validation applied to external Target Projects.
- The internal case study must document its pedagogical purpose, its relationship to the external-project generator and the commands needed to reproduce its validation.
- The presence or evolution of the internal case study must not modify, delete or silently overwrite the existing external demonstration project.

## Scope

- Includes: one repository-contained didactic Target Project
- Includes: versioned governed Target Project documentation
- Includes: a target-local Base Analysis registry
- Includes: a portable target-local VS Code workspace
- Includes: documentation of pedagogical purpose and reproduction commands
- Includes: validation through the existing explicit target_root checker
- Includes: preservation of the external Target Project generator
- Includes: preservation of support for external target destinations
- Includes: controlled refinement of case-study documentation during the experiment
- Excludes: versioning the existing external demonstration directory
- Excludes: nested Git repositories
- Excludes: host-specific absolute paths in versioned case-study configuration
- Excludes: replacing generator templates with the case-study corpus
- Excludes: treating the internal case study as an automated-test fixture
- Excludes: automatic BAE candidate extraction
- Excludes: automatic BAE registry authoring
- Excludes: automatic DFD generation
- Excludes: STRIDE or STRIDE-AI overlay analysis
- Excludes: security-driven documentation changes

## Acceptance

- The requirement is accepted when the ThreatForge repository contains one clearly identified and versioned Target Project case study outside canonical engine sources and test fixtures.
- The requirement is accepted when the case study contains no nested Git repository and no repository-user-specific absolute path.
- The requirement is accepted when the case-study provenance records that its initial structure was produced through the maintained Target Project generator.
- The requirement is accepted when the maintained generator still creates a canonically valid Target Project in an explicit external destination.
- The requirement is accepted when the repository-contained case study passes the existing Target Project checker using its internal path as target_root.
- The requirement is accepted when opening the case study as a VS Code workspace provides the target-local governed authoring, validation and Markdown assistance capabilities.
- The requirement is accepted when modifying the case-study documentation for pedagogical clarity remains subject to canonical Target Project validation.
- The requirement is accepted when the existing external demonstration directory is neither required for repository checks nor included in repository version control.
