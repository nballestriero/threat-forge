# MR-0004ADR-0002REQ-0001 — End-to-end common analysis-core case-study

## Intent

Demonstrate in one repository-contained Target Project the complete methodology-neutral analysis-core chain from governed documentation and Base Analysis through reviewed Common Findings to one governed Security Requirement.

## Functional obligation

- The repository-contained documentation-to-base-analysis Target Project must expose an end-to-end common analysis-core phase.
- The end-to-end phase must retain the existing governed documentation and Base Analysis corpus.
- The end-to-end phase must retain one explicitly simulated methodology-specific Analysis Record.
- The simulated Analysis Record must continue to declare that no methodology plugin is implemented.
- The simulated Analysis Record must remain not accepted for deterministic derivation.
- The end-to-end phase must retain explicit proposed accepted and rejected Common Finding review outcomes.
- The end-to-end phase must contain at least one manually authored Security Requirement.
- Every case-study Security Requirement must have one existing target-local Functional Requirement as its parent.
- Every case-study Security Requirement must be justified by one or more explicitly accepted Common Findings that affect its Functional Requirement parent.
- Every Finding used by a Security Requirement must remain navigable to its originating Analysis Record.
- Security Requirement content must remain independent from method identifiers classifications and method payload.
- Creating the Security Requirement must not modify the originating Analysis Record Common Findings Base Analysis records or Functional Requirement parent.
- The case study must distinguish the historical Common Finding-only phase from the current end-to-end phase.
- The end-to-end phase must remain validatable as a Target Project independently from implementation of STRIDE or STRIDE-AI plugins.

## Scope

- Includes: repository-contained documentation-to-base-analysis Target Project
- Includes: simulated methodology-specific Analysis Record
- Includes: explicit Common Finding review states
- Includes: accepted Finding to Security Requirement derivation
- Includes: Functional Requirement parent traceability
- Includes: Analysis Record provenance
- Includes: methodology-neutral Security Requirement content
- Includes: historical and current case-study phase distinction
- Excludes: production STRIDE plugin implementation
- Excludes: production STRIDE-AI plugin implementation
- Excludes: automatic Finding acceptance
- Excludes: automatic Security Requirement generation
- Excludes: changes to canonical Base Analysis caused by analysis execution
- Excludes: quantitative risk scoring
- Excludes: complete documentation-gap lifecycle
- Excludes: concrete security control implementation

## Acceptance

- The requirement is accepted when the Target Project contains one valid Security Requirement under an existing Functional Requirement.
- The requirement is accepted when the Security Requirement references at least one accepted Common Finding affecting the same Functional Requirement.
- The requirement is accepted when the accepted Common Finding resolves to its originating Analysis Record.
- The requirement is accepted when the Security Requirement contains no method identifier classification or method payload.
- The requirement is accepted when the Analysis Record remains explicitly simulated non-plugin evidence and not accepted for deterministic derivation.
- The requirement is accepted when the source Analysis Record Common Findings Base Analysis records and Functional Requirement remain unchanged by Security Requirement creation.
- The requirement is accepted when the case-study documentation identifies the historical Common Finding-only phase and the current end-to-end phase.
- The requirement is accepted when the Target Project passes canonical validation without a real STRIDE or STRIDE-AI plugin.
