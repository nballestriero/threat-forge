# MR-0004ADR-0002REQ-0001GOV-0001 — Phase-aware verification of the end-to-end analysis-core case study

## Intent

Ensure that progressive case-study validation preserves historical evidence, distinguishes simulated methodology evidence from implemented plugins and proves the methodology-neutral provenance of every manually authored Security Requirement.

## Governance obligation

- The case study must declare its current validation phase explicitly.
- The case-study documentation must identify the repository revision representing the historical Common Finding-only phase.
- The current end-to-end phase must not replace or reinterpret the capability claims of the historical phase.
- The simulated Analysis Record must continue to declare that its methodology plugin is not implemented.
- The simulated Analysis Record must continue to declare that automatic Finding derivation is not implemented.
- The simulated Analysis Record must remain not accepted for deterministic derivation.
- Common Finding review state must remain an explicit authored value.
- Common Finding review state must not be inferred from Analysis Record content.
- Every case-study Security Requirement must be created through an explicit governed authoring action.
- Every case-study Security Requirement must use an existing Functional Requirement from the Target Project as its parent.
- Every referenced Common Finding must be explicitly accepted.
- Every referenced Common Finding must affect the same target-local Functional Requirement.
- Every referenced Common Finding must retain navigable provenance to its originating Analysis Record.
- Security Requirement registry and body content must contain no methodology identifier classification plugin version or method payload.
- Security Requirement creation must leave the source Analysis Record Common Findings Base Analysis records and Functional Requirement parent unchanged.
- The current phase must remain valid without a production STRIDE or STRIDE-AI plugin.

## Verification obligations

- The verification must validate the declared current case-study phase.
- The verification must identify the historical Common Finding-only repository revision.
- The verification must confirm that the Analysis Record remains explicitly simulated and non-plugin.
- The verification must confirm that deterministic Finding derivation remains disabled.
- The verification must confirm that proposed accepted and rejected Finding states remain explicit.
- The verification must resolve every Security Requirement parent inside the Target Project.
- The verification must resolve every referenced Finding and require its review state to be accepted.
- The verification must confirm that each referenced Finding affects the Security Requirement parent.
- The verification must traverse each referenced Finding to one valid originating Analysis Record.
- The verification must reject methodology-specific data in Security Requirement registry or body content.
- The verification must compare protected source artifacts before and after Security Requirement authoring.
- The verification must exercise target-local command-line preview and confirmed creation.
- The verification must exercise the target-local VS Code schema association and authoring task.
- The verification must run the complete repository gate before milestone publication.

## Failure conditions

- The verification must fail when the current case-study phase is missing unknown or inconsistent.
- The verification must fail when the historical Common Finding-only phase is no longer identifiable.
- The verification must fail when the case study claims that a STRIDE or STRIDE-AI plugin is implemented.
- The verification must fail when the case study claims automatic Finding derivation.
- The verification must fail when the simulated Analysis Record becomes accepted for deterministic derivation.
- The verification must fail when a Finding review state is missing inferred or unsupported.
- The verification must fail when a Security Requirement parent does not resolve inside the Target Project.
- The verification must fail when a Security Requirement references a proposed rejected missing or unresolved Finding.
- The verification must fail when a referenced Finding does not affect the Security Requirement parent.
- The verification must fail when a referenced Finding has no navigable originating Analysis Record.
- The verification must fail when a Security Requirement contains methodology-specific data.
- The verification must fail when Security Requirement authoring modifies a protected source artifact.
- The verification must fail when target-local command-line or VS Code authoring assistance is stale or unavailable.
- The verification must fail when the complete repository gate fails.
