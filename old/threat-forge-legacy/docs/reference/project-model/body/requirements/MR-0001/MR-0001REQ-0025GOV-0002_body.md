# MR-0001REQ-0025GOV-0002 — Requirement registry field negative fixture coverage

## Intent

The Requirement registry field validator must prove that it fails closed for representative invalid Requirement registry states, not only that it passes the current repository state.

Negative fixtures make the validator's behavior deterministic for controlled status, type, specialized family, and parent Requirement rules.

## Parent Functional Requirement

Parent functional requirement: `MR-0001REQ-0025` — Requirement governance registry.

This specialized governance requirement hardens the Requirement governance registry by requiring fixture-backed evidence that invalid controlled values and invalid specialized parent relations are rejected.

## Specialized Requirement

The Requirement registry field gate must execute deterministic negative fixtures that model broken Requirement registry records and must fail if any fixture unexpectedly passes or emits the wrong diagnostic.

The negative fixtures must exercise the same validation logic used by the real repository check rather than relying only on separate hand-written assertions.

## Scope

This requirement applies to the `docs:requirement-registry-fields` gate and its Requirement registry field validator.

It covers representative negative cases for unknown Requirement status values, unknown Requirement type values, unregistered specialized family suffixes, missing specialized parents, unknown specialized parents, and specialized parents that are themselves specialized.

It does not require fixture coverage for every future Requirement registry rule, a full external test framework, mutation of the live repository, or validation of Requirement body Markdown sections beyond the existing Requirement body-format gate.

## Rules

- The Requirement registry field validator must discover negative fixture records from a deterministic repository path.
- Each negative fixture must be self-contained and must describe the minimal governance registry, decision registry, Requirement registry, and body files required for that fixture.
- Each negative fixture must be executed in an isolated temporary repository tree.
- The fixture run must use the same checker implementation as the real repository gate.
- A fixture must pass only when the checker exits non-zero for the invalid state and emits the expected diagnostic fragment.
- The real repository check must fail if a negative fixture unexpectedly passes.
- The real repository check must fail if a negative fixture fails for a diagnostic unrelated to the expected invalid state.
- The validator must avoid recursively running negative fixtures inside fixture executions.
- The implementation must include JSDoc traceability to this requirement.

## Acceptance Criteria

```gherkin
Scenario: Unknown Requirement status is rejected
  Given a fixture Requirement registry record declares a status outside the controlled status taxonomy
  When the Requirement registry field gate runs the negative fixtures
  Then the fixture run fails with a controlled-status diagnostic

Scenario: Unknown Requirement type is rejected
  Given a fixture Requirement registry record declares a type outside the controlled type taxonomy
  When the Requirement registry field gate runs the negative fixtures
  Then the fixture run fails with a controlled-type diagnostic

Scenario: Unregistered specialized family suffix is rejected
  Given a fixture specialized Requirement id uses a suffix outside the controlled specialized family taxonomy
  When the Requirement registry field gate runs the negative fixtures
  Then the fixture run fails with a specialized-family diagnostic

Scenario: Missing or invalid specialized parent is rejected
  Given a fixture specialized Requirement omits its parent, points to an unknown parent, or points to a specialized parent
  When the Requirement registry field gate runs the negative fixtures
  Then the fixture run fails with the expected parent diagnostic
```

## Verification Expectation

Running `npm run docs:requirement-registry-fields` must report the number of negative fixtures executed and must fail if any fixture no longer proves the expected invalid Requirement registry field behavior.
