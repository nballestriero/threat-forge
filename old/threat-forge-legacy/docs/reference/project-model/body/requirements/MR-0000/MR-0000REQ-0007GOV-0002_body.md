# MR-0000REQ-0007GOV-0002 — Governed commit-push execution path for project-model changes

## Intent

The project-model gate runner must become the governed path for repository commits and pushes, not only a convenience command for local checks.

This specialized requirement prevents operators from bypassing required governance checks by using direct `git commit` and `git push` commands after project-model changes.

## Parent Functional Requirement

Parent functional requirement: `MR-0000REQ-0007` — Runner unico MR-0000 per i gate di coerenza del project model.

## Specialized Requirement

The system must provide a governed commit-push command that executes the MR-0000 project-model gate sequence before staging, committing, and pushing repository changes.

The command must be the preferred operational path for committing and pushing governed project-model changes, so routine work cannot accidentally skip the configured checks.

## Scope

This requirement applies to the first governed repository operation runner for local development and handoff workflows.

It covers deterministic gate execution before commit, staging of non-ignored repository changes after successful checks, commit creation with an explicit message, push to the configured upstream, and failure propagation.

It does not introduce new validation semantics, replace specialized validators, define CI policy, or prevent an operator with direct shell access from manually running Git commands outside the governed workflow.

## Rules

- The governed commit-push command must run the existing project-model gates before creating a commit.
- The command must fail without committing when any orchestrated gate fails.
- The command must require an explicit commit message.
- The command must stage repository changes only after all orchestrated gates pass.
- The command must create the commit and push through Git only after the checks have succeeded.
- The command must use the repository's configured upstream instead of hard-coding a remote branch.
- The command must expose a check-only mode for local verification without creating a commit.
- The implementation must remain a thin orchestration layer and must not duplicate specialized validator logic.
- The implementation must include JSDoc traceability to this requirement, `MR-0000REQ-0007GOV-0001`, `MR-0000/ADR-0003`, and `MR-0000`.
- Future handoff instructions should prefer the governed commit-push command over direct `git commit` and `git push` commands once this requirement is implemented.

## Acceptance Criteria

```gherkin
Scenario: Governed commit-push succeeds
  Given the repository has governed changes ready to commit
  And every orchestrated project-model gate passes
  When the governed commit-push command is executed with a commit message
  Then the command stages the non-ignored repository changes
  And creates a commit with the supplied message
  And pushes to the configured upstream

Scenario: A gate fails before commit
  Given the repository has governed changes ready to commit
  When the governed commit-push command executes the project-model gates
  And one gate fails
  Then the command exits with a non-zero code
  And no new commit is created by the command
  And no push is attempted

Scenario: Commit message is missing
  Given the repository has governed changes ready to commit
  When the governed commit-push command is executed without a commit message
  Then the command exits with a non-zero code
  And no staging, commit, or push is attempted

Scenario: Check-only mode is used
  Given the repository may contain local changes
  When the governed runner is executed in check-only mode
  Then it runs the orchestrated gates
  And reports repository status
  And does not stage, commit, or push changes
```

## Verification Expectation

The implementation must be verified by running the check-only command and by using the governed commit-push command for the implementation commit itself after the drop-in is applied.
